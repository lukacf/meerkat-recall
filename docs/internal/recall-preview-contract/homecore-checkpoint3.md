**Q1 - signing-secret bytes.** `JWT_SECRET_FILE` calls `elephant_auth::service_token::read_secret_file`: it reads bounded UTF-8, then removes **all trailing CR and LF characters only** before HS256 signing/verification. It preserves other whitespace and embedded CR/LF. The resulting secret must have at least 32 bytes after the minimum-length check's whitespace trim; Unix files must have no group/other access and be regular files, at most 64 KiB. The service-token CLI uses this same file reader. An exact-byte HomeCore minter disagrees when the file ends in CR/LF. Either provision a file with no trailing CR/LF, or have that minter mirror UTF-8 validation and `rstrip(b"\r\n")`. `JWT_SECRET` environment input preserves its nonblank value; it does not perform the file reader's newline removal. No behavior change is being made silently.
