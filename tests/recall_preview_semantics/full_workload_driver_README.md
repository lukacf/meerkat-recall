# Fourteen-case workload driver

`full_workload_driver.py` composes G's bounded transport, controlled provider,
Graph preparation and 140-caller lexical components. Independent D owns the
case contract and expected results. The driver preserves actual request,
acceptance, head, operation, immutable revision and provider observations.
Every output retains `qualified: false` and `product_acceptance: false`.

The fourteen phases retain the original fifty corpus sources, two exactly
2,000,000-byte Retrieval sources, four shared Graph inputs, policy3/7 spaces,
original-intent no-op, held replacement/retraction, competing generation CAS,
actual Running/Pending/FailedRetryable observation, separate principal grant
revocation, current provider revocation, 140 ready callers, size fallback and
outage. Lifecycle phases operate sequentially in both spaces. A failed
prerequisite records dependent remaining phases as unexecuted. Original POSTs
are not automatically retried. The deliberate FW05 original-intent retry and
FW13 single limit20-to10 request are explicit cases, not transport retries.

The driver reads the actual immutable DocRevision DTO after publication. It
never reconstructs that record from a mutable Doc. Large Graph preparation
reuses the same two large source identities after Retrieval preparation; it
performs actual complete Graph publication before asking the enclosing artifact
owner for an export/compact-report capacity capture. No admission-only record
or scripted helper result qualifies full-pipeline storage/report capacity.

One `NamedClient` chooses immutable `space:role` credential entries while sharing
one physical request counter, deadline and capture budget. The original limits
remain 1800 seconds/backend, 8000 public HTTP calls, 4096 controlled provider
connections and 1 GiB capture. Every non-read public intent is durably recorded
before dispatch. Frozen Graph template hashes remain separate from the hash of
the actual request after binding only the originally observed head generation.
Expected rendered text, assertion semantics, spans, quotes and security are not
changed during binding. All actual returned identities come from public replies.

`full_workload.py inventory` is inert. `run` requires an exact SHA-pinned manifest,
original finite controlled-only allocation, source hashes, fresh installed
candidate startup custody, and original observed outbound-denial receipt for the
current distinct Linux network namespace. The CLI does not start a product
process, configure providers, create namespaces, stop arbitrary services, use
ambient tokens, or create a new allocation. It starts only its explicitly granted
IPv4 loopback controlled spy. It refuses the host namespace and absent isolation
proof. Backends are sequential under their original 3600-second total window;
the second requires the first terminal receipt. The whole allocation clock is
anchored before input validation, and cannot restart per phase or retry.

The independent case-plan v1 contains `contract_sha256`, exact `cases.FW01` through
`FW14`, `configurations`, `baseline_rendered`, `large_rendered`, `graph_recipes`,
`graph_recipe_sha256`, `spy_recipe`, `spy_recipe_sha256`, `load_plan`, and
`load_plan_sha256`. Large Graph literals may be separate original `{file:
{path,sha256}}` inputs, each at most 8 MiB; all input files together are bounded
by 32 MiB. The allocation independently pins the fully resolved canonical plan
hash. There is no shipped executable allocation or presumed approved plan.
D and E must finish and review concrete recipes/configuration/query expectations
before actual execution. Missing inputs leave the relevant capability unmet.

FW06–11 use two explicit `spaces` case entries. They identify independently
reviewed Graph recipe IDs and fixed public query bodies/expected fields. An optional `required_evidence` list has exact fields `source_key`, `revision`,
`quote`, and bare-hex `quote_hash`. Every required literal must occur in actual
returned evidence. Optional `required_claim_evidence` uses the same four fields
and must occur inside a `kind: claim` result; a surviving chunk cannot satisfy
canonical claim survival. Every result, including additional hits, must bind its full
UTF-8 raw `span`/`quote` to the original same-space input. Its `rendered_span`,
`rendered_quote_sha256` and `rendered_text_sha256` bind the selected interval and
full text of the actually observed immutable DocRevision. Original completed
operation/head identities, raw Source hash, immutable renderer, policy and
source-content provenance must agree. The required ninth field `doc_id`
is the canonical 40-byte `doc:<lowercase-hyphenated-UUID>` identifier. It must equal
both the original actual acceptance's Doc and the parent `doc` field of the
actually read immutable revision. This applies to claims, entities and chunks.
The parser refuses missing fields, an `internal_doc_id` alias, a different Doc, or changing
the evidence and immutable parent together while retaining the old acceptance.
It does not derive a parent from an external source key or a revision substring.
The existing nested public revision route and original coordinate fixture bytes
remain unchanged. The known text renderer v1 transform is
checked against an independent byte-origin map, with Rust's exact Unicode
whitespace set; passthrough v1 is exact identity. The smallest raw cover must
match, so equal quotations at a different occurrence, UTF-8 splits, generated-only
LF support, unknown renderer/configuration, and self-consistent changed rendered
text cannot pass. No substring matching, clipping or prefix quotation is used.
D's seven separately authored literal coordinate cases pin these expectations. Expected lists never guess future record IDs. Backlog
states must be observed through the exact original public operation routes;
a timer or held controlled response is insufficient. Grant revocation uses a
separate principal so unchanged source/head/operation/content can be read by an
independent still-authorized principal. Provider revocation requires an original
scheduled held 503 response; its release is observed under the revoked current
binding with no additional controlled-provider connection.

FW09 first admits and observes the failed-retryable source, then holds the
running source and submits the pending source. It requires fresh simultaneous
public Running/Pending/FailedRetryable observations, performs the original queries
and intake, then retracts the failed source through its current original head
before releasing the running source. Only the three surviving active intents
are expected to complete. FW11 accepts only its explicit original public failure
states, retains the actual error category, and retracts that original source
before restoring the binding. Each configuration mutation advances its actual
processing generation. Restoration retains the current storage-owned content
index epoch after cleanup and refuses any intervening authority change. In both
cases the old operation stays distinct
from the new retraction receipt/head. The exact source's original controlled
rule count is checked during cleanup and every later driver phase; idle provider
counts alone are not queue-drain proof.

The reviewed launcher first captures C's actual effective runtime inspector at
the `initial` boundary and passes that same object's async `capture` method as
`Driver(..., runtime_inspection=inspector.capture)`. FW09 refuses a missing
inspector, awaits `before_fw09_first_space` and `before_fw09_second_space`
before the respective named-space backlog sequence, and awaits
`after_fw09_cleanup` after both original cleanup sequences complete. The
callback returns `None`; C persists the actual observations in the shared capture.
An inspection refusal stops later cases, including FW11's intentional binding
changes. Each call uses the original workload clock; it cannot extend the
deadline. The small driver completion event records only successful callback
return and is not runtime evidence itself.

C's inspector owns proving the original process/instance and actual effective
queue, retry, document and provider recipes against I's reviewed expectations,
using original responses retained by the same transport and capture allocation.
S owns supplying explicit runtime-read credentials, the initial inspection and
the verified source inventory for every executed inspector dependency. A startup
`workers_enabled` boolean cannot substitute for this proof. The driver neither
derives runtime defaults nor adopts a replacement process; its callback tests
establish ordering and refusal behavior only. Until the enclosing producer and
launcher are coherently supplied and qualified, this seam remains unqualified.

FW12 passes the unchanged 280-request load plan and the independently pinned
`query_requirements`/`query_requirements_sha256` to G's load helper. The helper
uses this same synchronous full evidence verifier exactly once per successful
response, after retaining the original response. No new query, warm-up, changed
body, derived expectation or extra caller is introduced. A missing claim,
invalid extra hit or changed requirement pin prevents a positive protocol result.
All original deadlines, request/provider/capture bounds and owned task cleanup
remain in force.

The enclosing installed/container owner may supply `capacity_capture` and
`service_control` objects. Their methods capture the original export or stop the
owner's original service. FW10 uses the same named principal and shared HTTP
budget for actual MCP initialize/head, revoked typed refusal, and restored
original head through exact `/mcp/full`.
The driver accepts no PID, shell command, arbitrary stop endpoint or process
launcher. Missing hooks remain explicit unmet evidence; a public 404 cannot
establish physical erasure or backup/WAL/media closure.

FW13/FW14 import actual external consumer receipts with a separate run/backend/
owner/hash custody wrapper. S's CLI reader retains each original receipt and
optional independently approved expectation file as the same bounded, private
opened-file bytes (4 MiB each, within the unchanged 32 MiB aggregate input cap).
The driver preserves those exact bytes in its existing capture budget and checks
both hashes and the strict decoded receipt. It never re-encodes an object as an
original receipt. Missing original bytes cannot be reported as an imported
receipt; missing independent expectations leave accounting unmet.

For OB3, the driver calls D's `evaluate_receipt_bytes(raw_receipt,
raw_expectations)` with that exact pair. The oracle source is included in the
original CLI code-identity pins. The enclosing reviewed-byte bootstrap supplies
the callable as `Driver(..., ob3_oracle=verified_oracle.evaluate_receipt_bytes)`.
The driver neither opens the oracle path nor invokes a filesystem/bytecode-cache
loader after verification. A missing callable refuses evaluation; there is no
fallback import. The bootstrap separately owns proving that this callable and
the other helpers execute the original pinned source bytes. This adapter alone
does not establish that provenance. The driver test module's CLI inventory and
input controls enter that same reviewed snapshot loader and use its fresh
functional CLI and exception type; calling the uninitialized bootstrap's
inventory remains a refusal. These source controls require the enclosing CLI's
verified-byte bootstrap and do not authorize workload execution.
The new receipt version is
`ob3-recall-outage-2`; v1 remains historical and cannot pass the v2 consistency
oracle. Expected workers, POR baseline, source/run identity, original interval
and read bound must come from the independent original expectation allocation,
never from fields in the candidate receipt. D recomputes accounting and
participation; the driver adds no competing verdict rules. The original parsed
receipt, raw file references and complete scoped oracle result are retained.

A `pass` applies only to `external_receipt_consistency`, always with
`product_acceptance: false`. The driver keeps the full FW13/FW14 acceptance unmet
because receipt counters alone cannot prove physical size retries, process and
artifact custody, or a completed external consumer qualification. Failed,
malformed or zero-read originals are retained truthfully; producer PASS labels
never confer acceptance. HomeCore remains importable without an invented OB3
expectation schema. A real owner-controlled service outage can be captured
without claiming the consumer completed its work.

The old CB07 single 262145-byte quote cannot fit the installed default 12000-byte
extraction windows. It stays unsupported. Root approved D to review a replacement
using multiple actual grounded selected claims, each with complete supported
quotes, whose 20-result full JSON exceeds 262144 bytes and 10-result JSON fits.
The driver neither fabricates a 413 nor changes product extraction limits.

uses only scripted exchanges, memory gates and task-private captures. It checks
original ambiguous-submit custody, immutable generation binding, typed identity,
no-op state transitions, named credentials under concurrency, original deadlines,
failure propagation, external receipts, actual-owner outage capture and budget
refusal. These controls are not installed service, isolation, provider quality,
physical storage, semantic load or consumer acceptance evidence.
