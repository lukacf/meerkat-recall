Truth maintenance is the subsystem that turns multiple competing assertions into a single "current answer" for each subject-predicate pair. When two documents disagree about a claim -- for example, where someone works -- truth maintenance decides which claim wins, and why. Detection is **value-aware**: sources that agree corroborate each other, and only genuinely divergent values become conflicts. Real conflicts are resolved by an **LLM adjudicator** that sees the actual claim values, with deterministic policies as the fallback for deployments without an API key.

## Truth Slots

A **truth slot** represents the current best answer for a specific subject-predicate combination. It is the query-time view of resolved knowledge.

<CodeGroup>
```rust TruthSlot
struct TruthSlot {
    base: BaseFields,

    slot_key: String,          // deterministic key
    slot_type: String,         // "rel" | "attribute" | "event" | "rel_set"
    subject_entity: String,    // subject entity ID
    predicate_id: String,      // canonical predicate

    current_values: Vec<CurrentValue>,
    conflict_group: Option<Link<ConflictGroup>>,
    confidence: f32,
    rationale: Option<String>,

    // Versioning
    semantics_version: u32,
    alias_version: u32,

    // Staleness tracking
    stale: bool,
    stale_reason: Option<String>,
    computed_at: DateTime<Utc>,
    security_hash: String,
}
```
</CodeGroup>

### Slot Keys

The `slot_key` is a deterministic identifier computed from the claim's components:

- **For attributes:** `(subject_entity, attr_type, context_bucket?, security_hash)`
- **For relationships:** `(in, out, rel_type, security_hash)`
- **For rel sets:** `(subject_entity, __rel_set__, predicate_id, security_hash)` -- a cross-object slot that groups *all* objects a subject has for one predicate, so that "works_at ExampleCo" and "works_at ExampleLabs" can conflict even though they are different edges

Two claims with the same slot key compete for the same truth slot. The `security_hash` ensures that claims with different security envelopes do not silently merge.

<Note>
Because the security hash partitions slots, contradictions between claims in *different* security envelopes are never detected as conflicts. This is deliberate ABAC isolation: truth maintenance never joins data across envelope boundaries.
</Note>

### Current Values

Each truth slot holds one or more `CurrentValue` entries:

| Field | Type | Description |
|---|---|---|
| `claim_id` | `String` | Record ID of the winning claim |
| `confidence` | `f32` | Confidence score (0.0-1.0) |
| `status` | `ClaimStatus` | Status of the claim |
| `evidence` | `Vec<EvidenceRef>` | Supporting evidence references |

A slot may contain multiple current values (a coexist verdict, or the `AllowParallel` fallback policy) ranked by confidence, or a single winner after supersession.

## Corroboration vs Conflict

Detection partitions a slot's claims into **value groups** by exact value equality:

- **One value group, multiple claims -- corroboration.** Two sources asserting the same value agree; that is evidence, not a conflict. The slot commits directly with a `CorroboratedWinner`: evidence references from all members merge into the winner (deduplicated by assertion and span), duplicate rows are soft-deleted, and **no validity window is closed** -- a corroborating duplicate never "stopped being true."
- **Multiple value groups -- a real conflict.** The divergent claims form a `ConflictGroup` and go to resolution.

### Cross-object conflicts (rel_set)

Relationship slot keys include the object, so two different objects for the same subject and predicate occupy different slots. To catch contradictions like "works_at ExampleCo" vs "works_at ExampleLabs", detection also maintains **rel_set** slots per subject-predicate pair. A rel_set conflict group is created when a subject has more than one distinct object for a predicate **and** the predicate's configured cardinality is `One`, or its semantics are unknown. Predicates configured with cardinality `Many` (e.g. "speaks_language") and event-like predicates never produce rel_set conflicts.

## Conflict Groups

When divergent claims are detected, they are grouped into a `ConflictGroup`:

<CodeGroup>
```rust ConflictGroup
struct ConflictGroup {
    base: BaseFields,

    slot_key: String,
    slot_type: String,          // "rel" | "attribute" | "event" | "rel_set"
    claim_ids: Vec<String>,     // competing claim IDs

    resolved: bool,
    resolution_rationale: Option<String>,
    detected_at: DateTime<Utc>,
    resolved_at: Option<DateTime<Utc>>,

    // Adjudication memoization
    adjudicated_claim_set_hash: Option<String>,
    adjudicated_at: Option<DateTime<Utc>>,
}
```
</CodeGroup>

A truth slot links to its conflict group via `conflict_group` when unresolved conflicts exist. Once resolved, the group retains the rationale for audit purposes. The `adjudicated_claim_set_hash` memoizes the LLM verdict: as long as the group's claim set is unchanged, the conflict is never re-adjudicated -- including `needs_review` verdicts, and including re-corroboration of an already-superseded value.

## LLM Adjudication

When a real conflict exists and the pipeline has an Anthropic API key, resolution is performed by an LLM adjudicator that sees the rendered claim values, confidences, evidence counts, source timestamps, and any known predicate semantics. It returns a structured verdict (meerkat strict structured output with retries):

| Decision | Effect |
|---|---|
| `corroborate` | The claims turn out to agree (e.g. formatting variants). Evidence merges into a winner; duplicates are soft-deleted; no windows close. |
| `single_winner` | One claim wins; the others are superseded. |
| `coexist` | All values are valid simultaneously; every claim is approved. |
| `supersede` | A newer claim replaces older ones. The verdict carries validity dates the LLM read in the values (e.g. "left ExampleCo in 2024"), which take precedence over ingest timestamps when closing validity windows. |
| `needs_review` | Genuine ambiguity; flagged for human review. |

Verdicts may also include `equivalent_groups` -- claims that are the same value in different formats ("NYC" / "New York City"). Members of an equivalence group merge into their group winner exactly like corroboration.

### Learned predicate semantics

When the conflicted predicate has no registered semantics, the verdict **must** include proposed semantics (cardinality, temporal model, conflict policy). These are persisted to the predicate registry with `semantics_status: llm_proposed`:

- LLM-proposed semantics **never overwrite** operator-`configured` semantics.
- Later adjudications may revise non-configured semantics (e.g. a coexist verdict downgrades a `One`-cardinality proposal to `Many`).
- The upsert emits the standard predicate-registry outbox event, marking dependent truth slots stale so they recompute under the learned semantics.

### Deterministic fallback policies

Deployments without `ANTHROPIC_API_KEY` fall back to the predicate's declared `ConflictPolicy` (also used when adjudication fails after retries):

<Accordion title="AllowParallel (default)">
Both claims coexist in the truth slot. The slot shows all values ranked by confidence. Use this for predicates where multiple answers are valid simultaneously, such as "speaks_language" or "has_skill."
</Accordion>

<Accordion title="SupersedeByRecency">
The newer claim wins. The older claim's validity window is closed (its `validity_window.end` is set). Use this for predicates that represent mutable state, such as "works_at" or "lives_in."
</Accordion>

<Accordion title="SplitByContext">
Claims with different context buckets (e.g., different roles or time periods) do not conflict. Each context gets its own truth. Use this for role-dependent or context-dependent predicates.
</Accordion>

<Accordion title="RequireMoreEvidence">
No automatic resolution. The conflict is flagged for human review. Use this for high-stakes predicates where automated resolution is unacceptable.
</Accordion>

<Note>
Keyless deployments never supersede a value unless the predicate has operator-configured semantics that call for it. Cross-object (rel_set) conflicts without an adjudicator resolve as coexist rather than guessing a winner.
</Note>

## The Truth Maintenance Cycle

<Steps>
  <Step title="Detect">
    When a new assertion is resolved to entities and promoted into a relationship or attribute, the system computes its slot key and partitions the slot's claims into value groups. A single value group commits directly (first claim, or corroboration with evidence merge). Multiple value groups create or update a conflict group. Divergent objects for a single-valued predicate are caught via the rel_set slot.
  </Step>
  <Step title="Resolve">
    With an API key, the LLM adjudicator examines the actual claim values and returns a verdict (memoized per claim-set hash -- unchanged claim sets are never re-adjudicated). Without one, the predicate's conflict policy applies: `SupersedeByRecency` compares timestamps, `RequireMoreEvidence` flags the group for review, and so on.
  </Step>
  <Step title="Commit">
    The winning value is written to the truth slot's `current_values`. Superseded claims get their validity windows closed -- preferring dates the adjudicator extracted from the claims over ingest timestamps. Corroborated and equivalent duplicates merge their evidence into the winner and are soft-deleted. If the group's claim set changed between resolution and commit, the commit no-ops with a warning (stale-adjudication guard) and the slot is re-detected.
  </Step>
  <Step title="Recompute">
    When predicate semantics or alias mappings change, affected truth slots are marked `stale = true` with a `stale_reason`. A background job recomputes stale slots using the updated configuration. Recompute never calls the LLM inline: single-value-group slots commit deterministically, while multi-value-group slots enqueue `tm_resolve_slot` work items for adjudication. The `semantics_version` and `alias_version` fields track which versions were used for the current computation.
  </Step>
</Steps>

## Staleness

Truth slots track whether they need recomputation:

| Field | Description |
|---|---|
| `stale` | Boolean flag indicating the slot needs recomputation |
| `stale_reason` | Why the slot became stale (e.g., "predicate semantics updated") |
| `computed_at` | When the slot was last computed |
| `semantics_version` | Version of predicate semantics used |
| `alias_version` | Version of alias mappings used |

You can query for stale slots via the `list_truth_slots` API with `stale_only: true`.
