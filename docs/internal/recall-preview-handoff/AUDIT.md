## Readiness verdict

**Elephant deserves investment as Meerkat Recall. The audited implementation supports an incubating or preview designation; it does not yet justify the same trust expectations as a mature Core or Meta release.** The central idea is coherent and useful: retain source evidence, record interpretations, adjudicate conflicting claims, and return access-aware knowledge with provenance. Several implementation paths break those very guarantees.

The immediate work is substantial correctness and productization work. Preserve the domain model and existing useful machinery. Concentrate architectural changes on the owners of authorization, canonical commits, work attempts, and change propagation. Broad feature expansion would increase the qualification burden before these foundations are dependable.

**Production-exercised, but narrowly qualified** is the right description. HomeCore's operating history and retained acceptance receipts establish substantial real use. They also show that serious semantic and operational defects survived nominally passing tests. Its single-tenant deployment and bespoke recovery machinery do not exercise all the boundaries needed by independent consumers. The production interview below changes the assessment of experience, without dismissing the source-traced defects.

## How it hangs together

```text
Sources and retained input
  -> document rendering and immutable revisions
  -> document tree and extraction planning
  -> staged metadata / knowledge candidates
  -> validation and commit bundles
  -> assertions + entities + relationships + attributes + events
  -> outbox-driven truth maintenance and freshness
  -> search, provenance inspection, and derived Living Wiki views

HTTP / MCP / CLI / Rust facade
  -> runtime configuration and workers
  -> repositories
  -> SurrealDB OR the in-memory ElephantDB kernel
```

The source-first lifecycle and progressive metadata/retrieval/graph modes are a good foundation. A document-ingest request wraps a source rather than creating an unrelated pipeline. The active worker requires a real extractor for semantic readiness. Truth maintenance distinguishes corroboration from conflicting values, keeps configured predicate semantics authoritative, and isolates truth slots by security envelope. The Living Wiki has immutable revision receipts, dependency tracking, statement-local citations, independent verification, and explicit service grants. These are substantive implemented mechanisms. [Active ingest contract:56](https://github.com/lukacf/meerkat-recall/blob/7f8446856b3a9eb7b74976a406536e90d09c1cf6/docs/active-architecture.md#L56-L115) [Living Wiki contract:117](https://github.com/lukacf/meerkat-recall/blob/7f8446856b3a9eb7b74976a406536e90d09c1cf6/docs/active-architecture.md#L117-L170) [Truth-maintenance contract:257](https://github.com/lukacf/meerkat-recall/blob/7f8446856b3a9eb7b74976a406536e90d09c1cf6/docs/active-architecture.md#L257-L318)

**The main architectural weakness is that the intended invariants do not have one enforcement point.** HTTP and MCP implement overlapping policy and response logic. The Rust facade exposes trusted repositories. The worker owns important canonical writes through a sequence of repository calls. This allows a strong entity update guard to coexist with an unsafe relationship upsert, or MCP read-only mode to coexist with writable REST routes.

The storage abstraction also exposes SurrealQL and an embedded-store escape hatch rather than backend-neutral domain operations. Many repositories implement both branches. This is workable with a shared conformance suite, but it means maintaining two implementations of graph, mutation, and recovery semantics. The embedded kernel's transaction rollback, snapshot validation, and import barriers are valuable; they do not make its disk persistence equivalent to SurrealDB. [crates/storage/src/backend.rs:16](https://github.com/lukacf/meerkat-recall/blob/7f8446856b3a9eb7b74976a406536e90d09c1cf6/crates/storage/src/backend.rs#L16-L63) [crates/elephant-db/src/lib.rs:463](https://github.com/lukacf/meerkat-recall/blob/7f8446856b3a9eb7b74976a406536e90d09c1cf6/crates/elephant-db/src/lib.rs#L463-L494) [crates/storage/src/embedded.rs:119](https://github.com/lukacf/meerkat-recall/blob/7f8446856b3a9eb7b74976a406536e90d09c1cf6/crates/storage/src/embedded.rs#L119-L146)

The facade depends on the worker package under `bin/`, and runtime setup mutates process-global environment variables. This is a weak boundary for independently configured embedded instances. Move reusable composition into a runtime/application crate and inject immutable per-instance configuration. Keep the CLI and transport adapters thin. A low-level trusted repository escape hatch can remain explicit. [crates/elephant/Cargo.toml:10](https://github.com/lukacf/meerkat-recall/blob/7f8446856b3a9eb7b74976a406536e90d09c1cf6/crates/elephant/Cargo.toml#L10-L15) [crates/elephant/src/lib.rs:64](https://github.com/lukacf/meerkat-recall/blob/7f8446856b3a9eb7b74976a406536e90d09c1cf6/crates/elephant/src/lib.rs#L64-L106) [bin/elephant-api/src/runtime.rs:1186](https://github.com/lukacf/meerkat-recall/blob/7f8446856b3a9eb7b74976a406536e90d09c1cf6/bin/elephant-api/src/runtime.rs#L1186-L1238)

### F02. Protected input can produce baseline-classified knowledge (P1)

**New entity labels lose source classification.** Promotion passes extracted names into entity creation, which uses `BaseFields::new` without inheriting document security. The same promotion explicitly inherits security for assertions, events, attributes and relationships. A previously unknown confidential project or person's name can therefore become a default-policy entity, readable to a same-space principal with the corresponding default clearance and unrestricted subject scope. Entity display names, types and identity keys are themselves disclosures. [crates/pipeline/src/scheduler/inline_promotion.rs:214](https://github.com/lukacf/meerkat-recall/blob/7f8446856b3a9eb7b74976a406536e90d09c1cf6/crates/pipeline/src/scheduler/inline_promotion.rs#L214-L268) [crates/pipeline/src/scheduler/inline_promotion.rs:696](https://github.com/lukacf/meerkat-recall/blob/7f8446856b3a9eb7b74976a406536e90d09c1cf6/crates/pipeline/src/scheduler/inline_promotion.rs#L696-L724) [crates/types/src/records/base.rs:203](https://github.com/lukacf/meerkat-recall/blob/7f8446856b3a9eb7b74976a406536e90d09c1cf6/crates/types/src/records/base.rs#L203-L219)

[crates/pipeline/src/scheduler/inline_promotion.rs:1224](https://github.com/lukacf/meerkat-recall/blob/7f8446856b3a9eb7b74976a406536e90d09c1cf6/crates/pipeline/src/scheduler/inline_promotion.rs#L1224-L1285) [bin/elephant-api/src/routes/docs.rs:2038](https://github.com/lukacf/meerkat-recall/blob/7f8446856b3a9eb7b74976a406536e90d09c1cf6/bin/elephant-api/src/routes/docs.rs#L2038-L2078) [bin/elephant-pipeline/src/main.rs:5958](https://github.com/lukacf/meerkat-recall/blob/7f8446856b3a9eb7b74976a406536e90d09c1cf6/bin/elephant-pipeline/src/main.rs#L5958-L6084)

### F03. Failed grounding can still become an approved event (P1)

The active extractor preserves assertions when evidence is missing or mismatched, clearing the span/hash when necessary. Staged validation permits a zero-length span. Rehydration can replace a missing quote hash with a `derived:` hash of assertion fields and identifiers rather than source bytes. Promotion writes the assertion and can directly create an `Approved` event using the model's confidence. The precise problem is not that all stored assertions claim to be true: `Resolved` is identity resolution, and new relationships/attributes initially have Candidate status. The problem is that grounding failure has no enforced barrier preventing ordinary graph promotion and event approval. An evidence-shaped field or synthetic hash does not establish support. Later wiki citation checks do not repair earlier event or graph contamination.

**Required work:** represent grounded evidence, unsupported interpretation, and adjudicated claims as distinct states. Validate exact immutable source spans, UTF-8 boundaries, lineage and hashes before evidence-backed promotion. Keep unsupported candidates available for automated repair or re-extraction without granting normal evidence receipts or approval. Evaluate false canonical claims explicitly.

### F04. A partial canonical commit can become a successful incomplete retry (P1)

Promotion writes the assertion first, then the event and attribute/relationship, then the outbox. These are separate awaited storage operations. If a later write fails, the artifact is returned to Validated for retry. On the next attempt, finding the existing assertion causes the code to skip creation of missing downstream effects. It may enrich entities or refine an already-existing event, but it does not reconstruct a missing event, relationship, attribute or the original outbox records. The artifact can subsequently become Committed. [crates/pipeline/src/scheduler/inline_promotion.rs:152](https://github.com/lukacf/meerkat-recall/blob/7f8446856b3a9eb7b74976a406536e90d09c1cf6/crates/pipeline/src/scheduler/inline_promotion.rs#L152-L208) [crates/pipeline/src/scheduler/inline_promotion.rs:305](https://github.com/lukacf/meerkat-recall/blob/7f8446856b3a9eb7b74976a406536e90d09c1cf6/crates/pipeline/src/scheduler/inline_promotion.rs#L305-L308) [crates/pipeline/src/scheduler/inline_promotion.rs:447](https://github.com/lukacf/meerkat-recall/blob/7f8446856b3a9eb7b74976a406536e90d09c1cf6/crates/pipeline/src/scheduler/inline_promotion.rs#L447-L561) [crates/pipeline/src/scheduler/staged_commit.rs:223](https://github.com/lukacf/meerkat-recall/blob/7f8446856b3a9eb7b74976a406536e90d09c1cf6/crates/pipeline/src/scheduler/staged_commit.rs#L223-L247)

**Trigger:** a storage failure after assertion persistence and before the remaining canonical writes. This minimal failure path does not depend on a speculative process-crash sequence. Crash and timeout recovery face the same incomplete-effect problem once a retry reaches this branch.

**Required work:** prepare interpretation first, then atomically commit deterministic canonical rows, their outbox event and the commit receipt. Where one transaction is unavailable, use a durable per-effect ledger whose replay reconciles every expected effect. An assertion's existence must not stand in for completion of the whole promotion. This is the most important architectural repair.

### F05. Work recovery depends on unrelated queue activity and weak leases (P1)

**Isolated non-default spaces can stall.** The active claim path derives recovery spaces from runnable jobs, adding only the literal default space. ## A clean place in the Meerkat family

**Recommended product definition:** Meerkat Recall is an optional, independently usable knowledge and evidence service for agents and applications. It retains sources, resolves identities and conflicting claims, and returns provenance-bearing, access-aware retrieval. It can use Meerkat Core internally for model work without requiring callers to adopt Core or Meta.

| Owner | Keep this responsibility | Boundary with Recall |
| --- | --- | --- |
| Core | Agent execution, sessions, tools, transcript/compaction memory contracts, runtime authority. | Use Recall through ordinary tools or an explicit optional adapter. Recall does not become a required runtime store. |
| Meta / MobKit | Application composition, identity continuity, working memory selection/injection, operational policy and console projections. | Keep local working memory and turn availability. Integrate shared/world knowledge through a versioned provider or tool contract. |
| Recall | Evidence and knowledge lifecycle, identity/entity knowledge, retrieval, claim adjudication, provenance, access-aware derived views. | Own the knowledge semantics. Return typed facts, citations, uncertainty and freshness; do not acquire session or agent-lifecycle authority. |
| Connect | Future connector/acquisition capabilities, as that product's contract develops. | Treat connectors as source producers. A future integration must not delay or become mandatory for standalone Recall. |

Core already has a scoped conversation-memory trait with explicit atomic indexing and durability capabilities. Meta already has an optional `AgentMemoryProvider` with recall/write/delete and capability methods. Those are useful seams, but a whole knowledge graph need not be flattened into working-memory records. Start with a standalone service and a small supported adapter or tool bundle. ## How to use the findings in the preview

[PLAN.md](PLAN.md) contains the controlling delivery scope. The baseline's broad remediation directions above are not authorization to restore work deliberately removed from that scope. In particular, general legacy migration/backward compatibility is excluded; HomeCore owns its one-off transition. The proposed supported persistent backend and fresh-store product still need correct initialization, backup/restore and honest failure behavior.

Spaces, per-space configuration and authorized administration, isolation and recovery remain core requirements. Consumer review has also made source-scoped erasure a real adoption requirement; omitting person entities alone does not remove names from source text, embeddings, claims, provenance or backups. Follow the consumer-reviewed erasure and source-head contracts in the plan rather than inventing them independently from F06.

Baseline findings can leave the preview's implementation path only when the affected capability is genuinely unsupported and disabled across public entry points, scheduling, background work and replay. A disclaimer or hidden tool is insufficient. For retained behavior, the expected evidence includes:

- Refusal of unauthorized known-record access and consistent HTTP/MCP authority and capability behavior.
- Complete canonical effects and receipts under interrupted writes and replay, with stale attempts unable to publish.
- Source revision, retraction and erasure outcomes reflected in claims, evidence, search and queued work.
- Multi-space recovery and deliberately different per-space provider/configuration fixtures.
- Original-query retrieval and grounding evaluation, with missing prerequisites and skipped execution explicit.
- A supported independent installation and backup/restore procedure, qualified against the final named artifact.

The architecture is worth preserving. The key maturity work is to make its claimed boundaries enforceable and observable, then qualify the actual supported service and independent consumers. The audit alone does not certify a release.
