The supplied Compose file is a loopback development deployment. It uses local
database credentials and defaults to `SKIP_AUTH=true`. Use the setup below to
evaluate Elephant; build a production service configuration with explicit
credentials, authentication, TLS, storage, and rollback procedures before
serving remote callers.

## Architecture Overview

Elephant can run against either `surreal-db` (default) or embedded `elephant-db`.
The default Docker deployment starts `elephant serve` and `surrealdb`; standalone workers are optional:

| Service | Binary | Default Port | Description |
|---------|--------|--------------|-------------|
| `elephant` | `elephant serve` | 3000 | HTTP API server (Axum), MCP endpoints, and managed workers |
| `elephant-worker` | `elephant worker` | N/A | Optional standalone background workers |
| `surrealdb` | SurrealDB v2.4.1 | 8000 | Default persistent backend |

The API owns the managed runtime by default, including background worker loops. The pipeline can also run as a separate advanced worker deployment.

## Release binaries

For archive layout, checksum verification, installation, and model-backed demo
prerequisites, see [binary installation](/installation). The candidate matrix
and build instructions below describe intended artifacts; they do not establish
that a public download or clean-machine acceptance receipt exists.

The **Build release candidates** workflow is started manually for a selected
commit or ref. It validates the source, then builds native Linux x86-64 and
macOS ARM64 binaries with the `rocksdb` feature and default Meerkat extraction
support. Builds use Rust 1.94.0, the repository Cargo wrapper, `--locked`, and the
`deploy` profile. Linux uses Ubuntu 22.04 for compatibility with Debian 12.

Each candidate archive contains `elephant`, both license texts, and
`provenance.json` with the source commit/tree, build command, workflow run, and
binary SHA256. Its adjacent checksum file names the archive without directory
prefixes. The workflow attests its archives and uploads candidates; it does not
publish a GitHub release. Creating a version tag does not start another build.

To promote a release:

1. Select the reviewed source commit and confirm its CI checks passed. Verify
   that the proposed `vX.Y.Z` tag matches the workspace package version.
2. Download successful build artifacts, verify archive checksums and inspect
   their bundled provenance. Smoke test `elephant --help` on each target host.
   Keep the binary checksum, build source, and release source in the release
   record. If promoting an existing build from another commit, verify identical
   source trees or document and review the exact build-excluded differences.
3. Create the version tag at the reviewed release commit. Create a draft GitHub
   release with the verified archives, a flat `checksums.sha256` manifest, and
   release notes listing the actual supported platforms. Verify the uploaded
   bytes before publishing the draft. A locally prepared provenance file is
   descriptive evidence and is not a GitHub build attestation.
4. Before production activation, rehearse migrations on a consistent database
   backup and retain the previous executable and matching data/configuration
   for rollback. Verify health and representative application requests after
   activation.

For builds promoted outside the candidate workflow, record their actual build
commands and validation rather than claiming workflow attestations. Publishing
release binaries does not publish Rust crates or the local-helper npm package.

## Deployment Modes

<Tabs>
  <Tab title="Managed workers (default)">
    The default `docker compose up` runs `elephant serve` with managed workers in the same container. Storage is still SurrealDB by default.

    ```bash
    docker compose up -d
    ```
  </Tab>
  <Tab title="Separate workers">
    Custom deployments can run `elephant serve --server-only` and
    `elephant worker` as separate services against the same SurrealDB namespace
    and database. Configure the worker's extractor and maintenance MCP URLs to
    reach the API service, and supply an authenticated MCP token when needed.

    The supplied Compose file uses managed workers and does not include a
    separate-worker profile. Embedded `elephant-db` cannot share its in-memory
    state between processes.
  </Tab>
  <Tab title="Manual (Development)">
    For local development without Docker:

    ```bash
    # 1. Start SurrealDB
    docker compose up -d surrealdb

    # 2. Use one explicit database configuration for migrations and runtime
    export SURREALDB_URL=ws://localhost:8000
    export SURREALDB_NAMESPACE=elephant
    export SURREALDB_DATABASE=main
    export SURREALDB_USER=root
    export SURREALDB_PASS=root
    export SKIP_AUTH=true  # Local development only
    export ELEPHANT_HOST=127.0.0.1
    ./scripts/repo-cargo run -p elephant-bin -- migrate

    # 3. Start API server
    ./scripts/repo-cargo run -p elephant-bin -- serve --server-only

    # 4. (Optional) Start pipeline worker separately
    ./scripts/repo-cargo run -p elephant-bin -- worker

    # 5. (Optional) Run fully embedded mode instead of SurrealDB
    ELEPHANT_DB=elephant-db ./scripts/repo-cargo run -p elephant-bin -- serve
    ```
  </Tab>
</Tabs>

## Setup

<Steps>
  <Step title="Prerequisites">
    Install Docker and Docker Compose. SurrealDB v2.4.1 is pulled automatically.
  </Step>
  <Step title="Configure environment">
    Copy `.env.example` to `.env` and set required variables:

    ```bash
    cp .env.example .env
    ```

    The supplied Compose file selects OpenAI embeddings and an Anthropic
    extractor, so this setup needs both `OPENAI_API_KEY` and
    `ANTHROPIC_API_KEY`. A directly launched binary uses the provider selected
    by its own model and embedding settings. For a credential-free starting
    point, use the [local demo](/quickstart).
  </Step>
  <Step title="Start the database and apply schema">
    ```bash
    docker compose up -d surrealdb
    docker compose run --rm elephant elephant migrate
    ```

    This applies schema using the same service configuration as the server.
    For existing data, first rehearse against a consistent backup. Migrations
    are forward-only; rollback requires the matching database backup.
  </Step>
  <Step title="Start Elephant">
    ```bash
    docker compose up -d elephant
    ```
  </Step>
  <Step title="Verify health">
    ```bash
    # API health
    curl http://localhost:3000/v1/health

    # SurrealDB health
    curl http://localhost:8000/health
    ```

    Then inspect `GET /v1/runtime/status`: semantic ingestion needs storage,
    managed workers, and a real extractor to be ready. Submit and follow one
    representative document through [the ingest guide](/guides/ingesting-data).
    HTTP health alone does not establish that the pipeline can process data.
  </Step>
</Steps>

## Environment Variable Reference

The tables describe binary defaults unless a Compose override is stated.
Compose reads its `.env` file for substitution; running the binary directly
does not automatically source that file. Set variables in the environment
actually inherited by the process or use the managed runtime configuration.


### Core (API Server)

| Variable | Default | Description |
|----------|---------|-------------|
| `ELEPHANT_HOST` | `0.0.0.0` | Server bind address |
| `ELEPHANT_PORT` | `3000` | Server bind port |
| `ELEPHANT_DB` | `surreal-db` | Storage backend: `surreal-db` or `elephant-db` |
| `ELEPHANT_DB_SNAPSHOT_LOAD` | _(none)_ | Snapshot file to load at startup in embedded mode |
| `RUST_LOG` | `info` | Log level filter (see [Observability](/operations/observability)) |

### Authentication

| Variable | Default | Description |
|----------|---------|-------------|
| `JWT_SECRET` | _(required with authentication)_ | Random secret with at least 32 bytes for HS256 token validation |
| `JWT_ALGORITHM` | `HS256` | Only HS256 is supported by the current shared-secret decoder |
| `JWT_ISSUER` | _(none)_ | Required token issuer (optional) |
| `JWT_AUDIENCE` | _(none)_ | Required token audience (optional) |
| `SKIP_AUTH` | `false` | Skip authentication entirely |

<Warning>
  Use `SKIP_AUTH=true` only for isolated local development. With authentication
  enabled, startup rejects a missing/development/short secret or an unsupported
  algorithm. Generate a random secret, pass it through your secret manager,
  and do not commit it.
</Warning>

### SurrealDB Connection

| Variable | Default | Description |
|----------|---------|-------------|
| `SURREALDB_URL` | `ws://localhost:8000` | Database WebSocket URL |
| `SURREALDB_NAMESPACE` | `elephant` | Database namespace |
| `SURREALDB_DATABASE` | `test` for API/worker; `main` for migration CLI | Set explicitly and identically for all processes; `.env.example` uses `main` |
| `SURREALDB_USER` | `root` | Database username |
| `SURREALDB_PASS` | `root` | Local development database password; configure your own credentials for deployment |
| `SURREALDB_QUERY_TIMEOUT_SECS` | `30` | Embedded SurrealDB engine query deadline, positive integer seconds (1-86400) |
| `SURREALDB_TRANSACTION_TIMEOUT_SECS` | `30` | Embedded transaction limit; the shorter of this and query timeout bounds the query batch |
| `SURREAL_QUERY_TIMEOUT` | `30s` in Compose | Remote SurrealDB server query deadline; not an Elephant client-side limit |

<Note>
  `SURREALDB_*` variables only apply when `ELEPHANT_DB=surreal-db`. In Docker Compose, the SurrealDB URL is `ws://surrealdb:8000`; for local development, use `ws://localhost:8000`.
</Note>

Embedded SurrealDB deadline changes require a process restart. SurrealDB 2.6.5
does not enforce its transaction option independently, so Elephant applies the
shorter configured limit as its engine query-batch deadline. Remote connections
do not apply these client options to the server. See the
[capacity and retention guide](https://github.com/lukacf/elephant/blob/main/docs/work-queue-capacity.md)
for cancellation and archival details.

### MCP transport

| Variable | Default | Description |
| --- | --- | --- |
| `MCP_ALLOWED_HOSTS` | loopback hosts | Comma-separated remote hostnames or `host:port` values; loopback remains allowed |
| `MCP_ALLOWED_ORIGINS` | unrestricted by this optional origin filter | Comma-separated exact browser origins; scheme, host, and effective port must match |
| `MCP_BEARER_TOKEN` | _(none)_ | Bearer token for pipeline calls to authenticated Elephant MCP endpoints |

Requests without an `Origin` header remain accepted. The opaque `null` origin
requires an explicit entry. Host/origin checks do not replace JWT or ABAC.
For example, use `MCP_ALLOWED_HOSTS=elephant.example.com` behind a reverse proxy
and forward the corresponding host header.

### Embedded snapshots

Snapshot import/export is available only when `ELEPHANT_DB=elephant-db`.

| Variable | Default | Description |
|----------|---------|-------------|
| `ELEPHANT_SNAPSHOT_DIR` | _(none)_ | Optional base directory used to constrain snapshot import/export paths |

Operational helpers:

```bash
elephant snapshot export /tmp/elephant.json
elephant snapshot import /tmp/elephant.json
```

Paths are on the server host, not the CLI client's filesystem. Import replaces
the entire embedded store across all spaces. Follow the authentication and
whole-store scope requirements in the [snapshot reference](/api/system#embedded-snapshots)
and keep a verified export before replacing data.

<Accordion title="Embedding provider details">
  - **`fake`**: Returns deterministic synthetic vectors derived from the input bytes. Use for tests, not meaningful semantic similarity.
  - **`openai`**: Uses the OpenAI embeddings API. Requires `OPENAI_API_KEY`.
  - **`fastembed`**: Local ONNX-based embeddings via FastEmbed. No API key needed but requires the `fastembed` feature flag at compile time.
</Accordion>

## Migrations

Elephant uses SurrealQL migrations managed by `elephant migrate`:

```bash
# Use the same database environment as the running server.
# With Compose, inherit it from the elephant service:
docker compose run --rm elephant elephant migrate
```

<Warning>
  Migrations are forward-only. There is no automatic rollback. To revert, restore from a database backup and re-run migrations against the restored database.
</Warning>

## Docker Compose Reference

The `docker-compose.yml` defines two services:

- **`surrealdb`** -- SurrealDB v2.4.1 with file-based persistence (`surrealdb_data` volume). Health check via `/surreal is-ready`.
- **`elephant`** -- API server with managed pipeline workers. Health check via `GET /v1/health`.

The local ports bind to loopback. The skills directory is mounted read-only at
`/skills` in the Elephant container. Configure a separate production deployment
with database credentials, TLS, JWT authentication, and restricted network
access; publishing the development ports is not a production configuration.

## Stopping and Cleanup

```bash
# Stop services (preserves data)
docker compose down

# Stop and remove all data volumes
docker compose down -v
```
